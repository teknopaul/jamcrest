# GitHub Actions Release Plan

## Overview

One workflow file: `.github/workflows/release.yml`
Trigger: push of a tag matching `v*` (e.g. `git tag v0.1.4 && git push --tags`)

Three build jobs run in parallel, each uploading an artifact.
A final `create-release` job (depends on all three) creates the GitHub Release and
attaches all artifacts.

```
linux-build ──┐
macos-build ──┼──► create-release
windows-build ┘
```

---

## Linux — musl static binary

**Runner:** `ubuntu-latest` with an Alpine Linux Docker container

Alpine uses musl libc by default. Anything compiled inside the container is a musl
binary. Running the container on the Ubuntu runner is the standard GHA pattern for
producing musl binaries without a separate Alpine runner.

**Steps:**
1. Checkout repo
2. Run inside `alpine:latest` container:
   - `apk add build-base python3 nodejs-dev xxd git curl`
   - `bash setup/install-deps.sh`
     - If Alpine's `nodejs-dev` exposes linkable headers, it uses those (dynamic against musl's libnode)
     - If not, it falls through to `build-v8.sh` which builds `libv8_monolith.a` (static V8)
   - `make`
3. **Cache:** Key the V8 monolith build (`setup/_deps/v8/out/`) on the V8/Node version
   string from `setup/build-v8.sh`. First run is slow (30–60 min), subsequent runs
   are fast.
4. Strip the binary: `strip target/jamcrest`
5. Upload artifact: `jamcrest-linux-amd64`

**Result:** Single static binary, no glibc dependency, runs on any Linux distro
including old ones (CentOS 7, Debian Buster, etc.).

**Potential snag:** Alpine's `nodejs-dev` package may not expose `libnode` headers in
the same layout as Ubuntu's `libnode-dev`. If `install-deps.sh` falls through to the
monolith build that is fine — it already works, just slower. Worth checking Alpine's
package contents first.

## macOS — dynamic binary, no signing

**Runner:** `macos-latest` (Apple Silicon / ARM)

No Apple Developer ID, so no signing or notarization. Users who hit Gatekeeper run:
```
xattr -d com.apple.quarantine /usr/local/bin/jamcrest
```
Document this in the README. It is a one-time step and normal for unsigned CLI tools.

**Steps:**
1. Checkout repo
2. `bash setup/install-deps.sh`
   - This already handles macOS via brew (`brew install node` or equivalent)
   - Emits `setup/.v8.mk` with the correct header/lib paths
3. `make`
4. Upload artifact: `jamcrest-macos-arm64`

**Optional:** Also add `macos-13` runner (Intel/x86_64) and upload
`jamcrest-macos-x86_64` if Intel Mac coverage is wanted.

**Potential snag:** Brew's node headers live under a path like
`/opt/homebrew/include/node` which differs from the Ubuntu layout. `install-deps.sh`
already handles this via `try_libnode_dev()` but worth verifying the brew path is
covered. May need a brew-specific branch in the detection logic.

## Windows — Node.js shared build + NSIS installer

**Runner:** `windows-latest` (MSVC, Visual Studio Build Tools pre-installed)

This is the most complex job. The plan is:
1. Build Node.js from source with `--shared` to produce `node.dll` + `node.lib`
2. Compile `jamcrest.exe` linking against `node.lib` (import library for `node.dll`)
3. Bundle both into an NSIS installer

### Step 1 — Build Node.js shared (with caching)

```
git clone --depth 1 --branch v22.x https://github.com/nodejs/node.git node-src
cd node-src
.\vcbuild.bat shared dll release x64
```

Outputs (in `node-src\out\Release\`):
- `node.dll`
- `node.lib` (import library for linking)
- V8 headers under `node-src\deps\v8\include\`

**Cache key:** `windows-node-shared-v22-x64` (update version as Node LTS advances)
**Cache paths:** `node-src\out\Release\node.dll`, `node-src\out\Release\node.lib`,
`node-src\deps\v8\include\`

First run: 45–90 minutes. Cached runs: seconds.

### Step 2 — Compile jamcrest.exe

Add a Windows-specific make target or a small `build-windows.bat`:

```bat
cl.exe /std:c++17 /EHsc /O2 ^
  /I node-src\deps\v8\include ^
  /I node-src\include\node ^
  src\cpp\main.cpp src\cpp\v8_host.cpp src\cpp\cli_args.cpp ^
  /Fe:target\jamcrest.exe ^
  /link node-src\out\Release\node.lib
```

The embedded JS header (`src/cpp/embedded_js.h`) is generated by `xxd` — need
`xxd` available on the Windows runner (install via choco: `choco install xxd` or
use the Git for Windows bundled version).

### Step 3 — NSIS installer

Write `installer/jamcrest.nsi` (to be created):

```nsis
!define PRODUCT_NAME "jamcrest"
!define PRODUCT_VERSION "0.1.4"   ; injected from the tag at build time

Name "${PRODUCT_NAME} ${PRODUCT_VERSION}"
OutFile "jamcrest-windows-installer.exe"
InstallDir "$PROGRAMFILES64\jamcrest"
RequestExecutionLevel admin

Section "Install"
    SetOutPath "$INSTDIR"
    File "target\jamcrest.exe"
    File "node-src\out\Release\node.dll"
    EnVar::AddValue "PATH" "$INSTDIR"   ; adds to system PATH
    WriteUninstaller "$INSTDIR\uninstall.exe"
SectionEnd

Section "Uninstall"
    Delete "$INSTDIR\jamcrest.exe"
    Delete "$INSTDIR\node.dll"
    Delete "$INSTDIR\uninstall.exe"
    RMDir "$INSTDIR"
    EnVar::DeleteValue "PATH" "$INSTDIR"
SectionEnd
```

Run in CI: `makensis installer\jamcrest.nsi`
(NSIS is available on `windows-latest` runners; if not, `choco install nsis`)

Upload artifact: `jamcrest-windows-installer.exe`

## Release job

Runs after all three build jobs succeed.

```yaml
create-release:
  needs: [linux-build, macos-build, windows-build]
  runs-on: ubuntu-latest
  steps:
    - uses: actions/download-artifact@v4
    - name: Create release and upload assets
      run: |
        gh release create "$GITHUB_REF_NAME" \
          jamcrest-linux-amd64 \
          jamcrest-macos-arm64 \
          jamcrest-windows-installer.exe \
          --title "jamcrest $GITHUB_REF_NAME" \
          --generate-notes
      env:
        GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

`--generate-notes` auto-populates release notes from commits since the last tag.

## Versioning

The tag IS the version. In the workflow, `$GITHUB_REF_NAME` gives `v0.1.4`.
The NSIS script and any version strings should be injected at build time:

```yaml
- name: Set version
  run: echo "VERSION=${GITHUB_REF_NAME#v}" >> $GITHUB_ENV
```

Then pass `VERSION` into the NSIS script via `/D` flag:
```
makensis /DPRODUCT_VERSION=${{ env.VERSION }} installer\jamcrest.nsi
```

The `version` file and `pom.xml` should be updated before tagging (manual step,
or a separate `bump-version` workflow).

## Open questions before implementation

1. Does Alpine's `nodejs-dev` expose headers in a layout compatible with `v8_host.h`
   (`#include <v8.h>` and `#include <libplatform/libplatform.h>`)?
   Quick check: `apk info -L nodejs-dev | grep v8`

2. Does `install-deps.sh` need a brew-specific path added for macOS header detection?

3. Does `node.dll` from the `--shared` Node.js build export the raw V8 C++ symbols
   that `v8_host.cpp` links against, or only the Node.js API (`napi_*`)? If only NAPI
   is exported, the Windows approach needs to change to building `libv8_monolith.lib`
   from the V8 source directly (same effort, different target).
